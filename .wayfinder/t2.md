## Question

ADR-0012 records that the Drive cold archive is **not functioning**, and the local environment confirms it: `GOOGLE_REFRESH_TOKEN` and `GOOGLE_DRIVE_FOLDER_ID` are absent from `.env.local` while `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` are present. The daily cron at 20:00 UTC (`daily-drive-backup` → `scheduledBackup`) calls `uploadSnapshotBackup`, which throws `Missing Google OAuth credentials`.

An archive nobody can write is not an archive. What exactly must be repaired, and what is the smallest change that makes the Drive path trustworthy?

## Sub-questions

- **Credentials.** What scopes does the refresh token need, and does the existing token have them? Reading archived files back (for the browser) is a _different_ scope from writing them — Drive's `drive.file` covers only files the app created, which may be exactly right here.
- **Folder.** Is `GOOGLE_DRIVE_FOLDER_ID` set to a real folder, and does the service account/user actually have write access to it?
- **The shared-folder decision.** Grilling settled on sharing the HWIS folder with the system named in the filename (`esl-archive-2026-2027.json` beside `hwis-backup-*.json`) rather than a second folder. Confirm this does not need a second folder ID, and that one refresh token can serve both.
- **Failure visibility.** Today a failed upload is a thrown error inside a cron — invisible. Should a failed archive write an `audit_logs` row or a `backups` row recording the attempt, so "the archive did not happen" is discoverable rather than silent?
- **Existing e2e hygiene.** Issue #133 already covers separating test backups from production on Drive. Does this work depend on it, or must it not collide with it?

## Why this blocks

The file shape ticket can be decided without it, but the browser ticket cannot: if Drive reads are not in scope for the token, the browser must fetch the file by another route entirely.

## Out of scope

- Migrating the existing HWIS daily backup onto a new folder.
- Any change to the retention/prune schedule.
