## Question

Grilling settled the archive is written by a **separate manual action**, run by an admin _after_ the year has been advanced and verified — not folded into `advanceGrade`. What does that action actually do, and how does it behave when it goes wrong?

## Sub-questions

- **Ordering.** The archive is the last step, and must be verified before the deletion it precedes. Is it a plan-then-apply pair (mirroring `planYearAdvancement` / `advanceGrade`, which is the house pattern), or a single mutation with a confirmation dialog?
- **Upload before delete.** The file must be confirmed on Drive _before_ any Convex row is deleted. Is that a hard gate — a failed upload leaves Convex untouched — and is it verifiable (check the uploaded file's size, or read it back) rather than trusting a 200?
- **Idempotency.** `advanceGrade` refuses to double-write on re-run by design. What does re-running an archive do — refuse, report already-archived, or re-upload? And what happens if the upload succeeded and the deletion did not?
- **Auth.** `requireEslAdmin` presumably, but this deletes rows and writes to the school's Drive. Does it need a stronger gate — the `requireAdminForSensitiveOperation` path that the CAS year-end migration uses?
- **Partial failure.** Convex mutations are not transactional across thousands of writes. If deletion dies halfway, is the year left in a state a re-run can recover from? What does the admin see?
- **Reporting.** `advanceGrade` returns a reason string; `runYearEndMigration` returns counts. What does a successful archive report — file id, counts archived, year?

## Why this matters

This is the ticket that decides whether the archive is safe to run once a year on real data with no rehearsal. The failure mode is silent data loss: rows deleted, file never confirmed written.

- What the file contains (a separate ticket).
- The read-only browser.
