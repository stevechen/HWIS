## Question

Grilling settled the archive is **read-only**, browsed in-app — because a JSON file readable only in a text editor will not be consulted during a real accreditation request. What does that browser look like, and where does the file come from at read time?

## Sub-questions

- **The fetch path.** Convex Node actions can reach Drive. So: download the year's file from Drive on demand and parse it? Or list-and-read through the Drive API? What does that cost under ADR-0021's quota-first rules — a whole year of rosters is hundreds of rows.
- **Where it lives.** `/esl/admin/archive?year=2026-2027`, next to the existing `/esl/admin/*` pages? What does an admin see when they open it with no year chosen?
- **What is readable.** Cohorts with their classes, rosters by class, the teacher names? Enough to answer "what did G9 Intermediate 1 look like at the end of that year"? Does it need per-student evaluation history (there is none for ESL) or class rosters only?
- **Guarantees.** Read-only means no mutation affordances at all — no restore, no edit, no re-archive. Confirm that, and confirm what happens if the Drive fetch fails (an empty page must not read as "that year had no students").
- **Discovery.** How does an admin know which years are archived? Listing Drive folder contents as the index is one option; a row in Convex recording each archive is another, and the second is more robust but means Convex keeps a trace of what it deleted.

## Carried in from #144

The Drive scope choice is a live fork here, not a settled fact. With `drive.file` the app sees only files it created — enough to _read_ an archive it wrote, but **not** to list the shared folder as its index. With `drive` it sees the whole folder. So: if the browser discovers archived years by listing Drive, the token needs `drive`; if Convex keeps a row per archive, `drive.file` suffices. Answering "Discovery" above answers the scope question too.
